## The bug report

A user installed yaoe-flow as a `systemd --user` service (unit generated by `yaoe-flow setup`'s System service step). Right after boot, the journal showed a raw, unstructured `ACP write error: ... EPIPE: broken pipe` dump (no Pino formatting, garbled minified source context). Later, during a scheduler tick, the `claude-code` harness failed with `acp timeout: initialize (15000ms)`. The `cursor` harness worked fine in the same run (33 models enumerated). Running `yaoe-flow daemon` directly from an interactive terminal on the same machine had no issue at all.

## Diagnosis

First cleared a red herring: the `EPIPE` dump is not our code and not a crash. It comes from the vendored `@zed-industries/agent-client-protocol` library (`#sendMessage`'s `.catch((error) => console.error("ACP write error:", error))` in `node_modules/@zed-industries/agent-client-protocol/typescript/acp.ts`) — it already catches the write failure and keeps its internal write queue going. The daemon stayed healthy afterward (Valkey connected, the tick completed).

The real, reproducible symptom: `claude-code-acp` (the ACP adapter package `app/src/agent/harness/claudeCode.ts` spawns) is an npm package with a `#!/usr/bin/env node` shebang. Confirmed on the user's machine:

```
$ which node
/home/lucas-souza/.nvm/versions/node/v24.18.1/bin/node

$ env -i HOME="$HOME" PATH="<the systemd unit's exact PATH>" claude-code-acp --version
/usr/bin/env: 'node': No such file or directory
```

`node` was only ever reachable through nvm's versioned directory — never in the systemd unit's `Environment=PATH=...` (a fixed list: `~/.yaoe-flow/harness/bin:~/.local/bin:~/.bun/bin:/usr/local/bin:/usr/bin:/bin`), nor in yaoe-flow's own runtime PATH patching (`harnessPathCandidates()` in `app/src/cli/setup/harnessDeps.ts`, which only covered `~/.local/bin`, `~/.bun/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, plus its own `~/.yaoe-flow/harness/bin`). An interactive shell works because `~/.bashrc`/`~/.profile` (sourced by nvm's own install hook) puts the active version's `bin` on PATH — a service manager only ever gets what's in its own unit file.

`yaoe-flow doctor` (run under the same restricted PATH) reported `⚠️ harness Claude Code: installed, auth unknown` — misleading, since the adapter can't actually execute. See [A related detection false positive](#a-related-detection-false-positive).

## The fix

`harnessPathCandidates()` (`app/src/cli/setup/harnessDeps.ts`) — consumed by `ensureHarnessBinOnPath()` → `withHarnessSpawnEnv()`, which runs before **every** ACP adapter spawn (`app/src/agent/harness/acpAdapter.ts` lines 78/148, covering both detection and real session runs) — now also probes for a Node version manager's bin dir:

- **nvm**: reads `~/.nvm/alias/default` and resolves it against `~/.nvm/versions/node/*`; falls back to the highest installed version (plain semver-ish sort) if the alias file is missing or points at something not installed.
- **Volta**: `~/.volta/bin` if it exists (fixed shim path regardless of active version — no alias resolution needed).

Because this patches `process.env.PATH` inside the running daemon process itself (not the systemd/launchd unit file), the fix is **self-healing on upgrade** — no need to regenerate or hand-edit the existing unit. Only covers nvm and Volta (the two most common cases); asdf/fnm/`n` users still need to add their bin dir to the unit's `Environment=PATH=...` manually (documented in `docs/harnesses.md`).

## A related detection false positive

`detectByVersionFlag()` (`app/src/agent/harness/acpAdapter.ts`) treats "nonzero exit code but some output" as "installed" (a deliberate leniency for CLIs that print version info alongside warnings on a nonzero exit). A missing shebang interpreter falls into exactly this bucket — `/usr/bin/env` prints `'node': No such file or directory` to stderr and exits nonzero, which is non-empty output, so the generic heuristic reported "installed, auth unknown" instead of "not installed". Added a narrow, specific check: output matching `/usr/bin/env: .*No such file or directory` now reports `installed: false` with the missing-interpreter detail appended to the install hint, without touching the general (and still useful) "nonzero exit + some output = installed" fallback for every other harness.
